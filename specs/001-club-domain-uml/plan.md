# Implementation Plan: UML-діаграми предметної області спортивного клубу

**Branch**: `001-club-domain-uml` | **Date**: 2026-11-20 | **Spec**: [специфікація](./spec.md)

**Input**: Специфікація функції з `/specs/001-club-domain-uml/spec.md`

## Summary

Створити узгоджений, виключно текстовий комплект UML-діаграм і CRC-карток для предметної області спортивного клубу. План охоплює діаграму варіантів використання PlantUML, Mermaid-діаграми класів, послідовності та станів, а також XLSX-книгу CRC-карток для всіх сутностей предметної області. Результатом є перевірюваний комплект у каталозі `docs`, без мережевої, файлової або базданої реалізації.

## Technical Context

**Language/Version**: Виконавчий код не генерується; матеріали у форматах PlantUML, Mermaid і XLSX.

**Primary Dependencies**: Засоби рендеринга PlantUML/Mermaid; для генерації XLSX можна використовувати стандартну бібліотеку Python або еквівалентну підтримувану бібліотеку.

**Storage**: Текстові `.puml`/`.mmd`-файли та `.xlsx`-книга в каталозі `docs/`; база даних не потрібна.

**Testing**: Синтаксична перевірка діаграм, перевірка XML/XLSX, контроль імен і зв'язків, порівняння набору CRC-класів із діаграмою класів.

**Target Platform**: Текстові редактори, засоби рендеринга діаграм і переглядачі XLSX.

**Project Type**: Навчальний предметний набір матеріалів; консольна предметна логіка без графічного інтерфейсу.

**Performance Goals**: Статичні артефакти мають рендеритися однозначно і повністю.

**Constraints**: Реальні платежі, мережа, БД і зовнішні API поза обсягом; зовнішні операції моделюються через повідомлення наміру.

**Scale/Scope**: 10 ключових сутностей, 3 дійові особи, 4 основні бізнес-сценарії та 5 вихідних артефактів.

## Етапи виконання

### Phase 0: Research

1. Зафіксувати рішення щодо форматів і інструментів генерації.
2. Уточнити правила узгодження імен у всіх діаграмах.
3. Визначити мінімальний набор сутностей і зв'язків для дидактичної моделі.
4. Записати всі рішення й альтернативи в `research.md`.

### Phase 1: Design

1. Побудувати модель сутностей, атрибутів, методів, зв'язків і станів в `data-model.md`.
2. Спроєктувати назви й сигнатури класів та методів так, щоб кожне посилання на інший клас відповідало зв'язку.
3. Визначити послідовність сценарію купівлі абонемента й бронювання як основний приклад класно-послідовнісної узгодженості.
4. Підготувати `quickstart.md` із перевірками рендеринга, консистентності і CRC-книги.

### Мета реалізації артефактів

| Артефакт | Обов'язковий вміст |
|---|---|
| `docs/usecase.puml` | 3 актори і всі ключові варіанти використання |
| `docs/class.mmd` | Наслідування, реалізація, залежність, агрегація або композиція |
| `docs/sequence.mmd` | Лише об'єкти з іменами класів предметної області |
| `docs/state.mmd` | Початковий і кінцевий стани, купівля, бронювання, заморожування й поновлення |
| `docs/crc.xlsx` | Одна картка для кожного класу предметної області без пропусків і дублікатів |

### Перевірки узгодженості

- Усі три актори мають щонайменше один scenario link.
- Набір імен в об'єктах послідовнісної діаграми точно дорівнює класам діаграми класів.
- `Membership` посилається на `AccessControlSystem`, а `Visit` має агрегаційний або композиційний зв'язок із класом предметної області.
- `ClubParticipant` є абстрактним батьком для `ClubMember`, `Instructor` і `Administrator`.
- Всі три похідні класи реалізують `IClassSchedule`.
- Кожен клас має атрибут або метод, а створення екземплярів відображає конструктор.
- Щонайменше один метод позначено `final`.
- CRC-книга містить два стовпці з точними українськими заголовками «обов'язки класу» та «з ким співпрацює».
